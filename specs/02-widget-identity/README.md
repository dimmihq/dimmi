# 02 Widget identity (JWT verification)

Style: caveman. Date 2026-11-01. Backend only. Copy-paste server helpers in [snippets.md](snippets.md). Edge cases [edge-cases.md](edge-cases.md). Build order [tasks.md](tasks.md).

Sibling spec: [01-messenger-widget](../01-messenger-widget/README.md) owns sessions, boot handshake routes (`POST /widget/v1/sessions`, `GET`/`PATCH`/`DELETE /widget/v1/session`), widget channel. 02 owns: identity secrets, token verification, claims to contact mapping, lead-to-user merge on login, identity error language. 01 calls 02 actions; 02 never serves widget routes.

## Goal

Host app proves "this visitor is user 42" with signed JWT. Dimmi trusts only signed claims, never typed ones. Secure by default, five-minute setup, every failure explained in plain words.

Why: roadmap launch item 2 ("Secure identity by default"). Intercom shared-device leaks and silent JWT failures (`research/competitors/fin.md`, onboarding step 5 and 6) are what vibe coders hit. Intercom deprecated `user_hash` HMAC in 2026; JWT is primary.

## World-class bar (measurable)

| Bar | Target |
|---|---|
| Setup | secret created to first verified session under 10 minutes with snippet; under 2 minutes via `npx dimmi init` (09) |
| Default | verification always on (no mode switch): plain `user_id`/`email` from browser never identifies anyone |
| Verification cost | HS256 verify p95 under 0.2 ms; whole identity step in session start/resume p95 under 5 ms when claims unchanged (zero writes) |
| Explainability | 100% of error codes have plain sentence + fix hint |
| Zero-downtime rotation | 2 secrets valid at once; retire with grace; rotate in one API call |
| Shared-device safety | identified session never resumes without JWT for same `sub`; `logout()` leaves zero local state and revokes server side |
| Leak proof | unverified data never reaches verified history: dedicated test suite (rules R1 to R8 below) blocks merge |

## Scope

### In (MVP)

- Fixed behavior, no per-workspace mode (Identity behavior section).
- `identity_secrets`: HS256 shared secrets (generated by Dimmi, shown once), RS256 and EdDSA (Ed25519) public keys uploaded by host (host keeps private key). Multiple active, `kid` = secret public id. Rotate, retire with grace, revoke (optionally kill sessions).
- Verification service per RFC 7519 + RFC 8725 best practices: alg allowlist pinned per key, `none` rejected, `exp` required, leeway 60 s, lifetime cap, optional `aud`, optional single-use `nonce` (Valkey replay cache). Built on go-jose v4 under strict `framework/jwt` wrapper. Surfaces: `widget` (01 handshake) and `portal` (14 feedback portal SSO).
- Claims schema: `sub`, `email`, `email_verified`, `name`, `phone`, `phone_verified`, `avatar_url`, `locale`, `timezone`, `company {id, name, domain, custom_attributes}`, `custom_attributes`.
- `IdentifyVisitor`: upsert user contact, upgrade or merge lead on mid-session login, company upsert, verified identity rows, member-email test detection. `IdentifyContact` (no widget, no session) for 14 portal SSO.
- Token transport: identity source (01 sdk-contract "Identity sources": Next server action, same-origin identity URL, identity function); SDK sends token on 01 handshake as wire field `user_jwt` (`POST /widget/v1/sessions`, `PATCH /widget/v1/session`). No SDK option named `user_jwt`.
- `Dimmi.logout()` server semantics.
- Plain-word error codes + hints on 401 (01 session routes) and console; MCP status tool.
- Snippets API + docs content ([snippets.md](snippets.md), single source): helpers `@dimmi/nextjs` (+ auth adapters) and `@dimmi/server` (Fetch handler, `/express`, `/hono`), raw snippets for every other stack (Node no deps, edge `jose`, Python PyJWT + Django/FastAPI, Go golang-jwt, Rails ruby-jwt, PHP firebase/php-jwt + Laravel), portal SSO link helpers (14).

## User stories

- Owner: create secret, paste into `.env`, see verified contacts in inbox.
- Developer (Next.js + Clerk): `identify: clerk()` in `dimmi.config.ts`; never touches JWTs.
- Developer: bad token, read console "Token expired 3 minutes ago." + fix hint.
- Developer: rotate leaked secret in one call; old one keeps working 7 days or dies now with all sessions.
- End customer: log in on laptop, see same conversations as on phone. Log out on library PC, next person sees nothing.
- End customer (attacker): types CEO's email in widget; sees nothing of CEO's history. Ever.
- AI agent (Claude Code via MCP): read identity status (secrets configured, next step) while wiring auth.

## Identity behavior (fixed, no modes)

| Input | Behavior |
|---|---|
| identity token | always verified; valid = identified user; invalid = 401 on 01 session route (no side effects), SDK continues anonymous, loud console error |
| plain `user` hints | accepted as unverified lead attributes only (R5) |
| anonymous visitors | allowed unless 01 `allow_anonymous = false` |

No secret exists: JWT session starts fail `identity_not_configured` (401, SDK continues anonymous); anonymous works.

## Token verification (ordered, first failure wins)

1. Size at most 8 KB; three base64url segments; header and payload JSON objects. Else `token_malformed` / `token_too_large`.
2. Header `alg` in workspace-allowed set (`HS256`, `RS256`, `EdDSA`). `none` and anything else: `token_alg_not_allowed`. `crit` present: `token_malformed`. `typ` if present must be `JWT` (case-insensitive).
3. Key selection: `kid` present: secret by public id in workspace. Not found: `token_kid_unknown`. Revoked: `token_secret_revoked`. `kid` absent: HS256 only, try every `active` and `retiring` HS256 secret (max 5, constant-time compare each). RS256/EdDSA without `kid`: `token_kid_required`.
4. Header `alg` must equal key `algorithm`: else `token_alg_mismatch` (blocks alg confusion).
5. Signature: HMAC-SHA256 (key = UTF-8 bytes of full secret string), RSASSA-PKCS1-v1_5 SHA-256 (key at least 2048 bits), Ed25519. Fail: `token_signature_invalid` (static hint lists common causes).
6. `exp` required (`token_exp_missing`), number. `now > exp + leeway`: `token_expired`.
7. `nbf` and `iat` (if present): `now + leeway < nbf` or `iat > now + leeway`: `token_not_yet_valid` (hint shows clock offset).
8. Lifetime: `exp - (iat or now) > identity.max_token_lifetime` (7 days): `token_lifetime_too_long`.
9. `aud`: surface `widget`: optional; if present, string or array containing `dimmi`, the widget app id `wgt_...`, or workspace id `ws_...`. Surface `portal`: required, must contain `dimmi-portal` (portal tokens never double as widget tokens and vice versa). Else `token_audience_mismatch`.
10. `sub` required string 1 to 255 chars after trim, no control chars. Number: converted to decimal string, warning `claim_sub_number`. Else `token_sub_missing` / `token_sub_invalid`.
11. `nonce` (if present, max 128 chars): Valkey `SET NX EX` key `identity:nonce:{workspace}:{sha256(nonce)}` with TTL `exp - now + leeway`; key exists: `token_replayed`. Rebuildable state only (lost cache = replay window until `exp`, bounded by 10-minute helper tokens and 300 s portal tokens). Valkey unavailable: tokens with `nonce` fail closed (503, SDK retries on next trigger), tokens without `nonce` unaffected. `jti` ignored (no replay semantics).
12. Optional claim shape errors (bad email, phone, company, custom attribute): claim dropped, token still valid, warning code `claim_<name>_invalid` returned in `identity.warnings` and console.
13. Update `identity_secrets.last_used_at` (throttled 1 per minute per secret, in-memory coalesce).

Clock: `framework/clock` (`a.Clock`). Leeway `identity.clock_leeway` 60 s.

`VerifyIdentityToken{WorkspaceID, AppID?, Token, Surface}`: `Surface` in (`widget`, `portal`). Same steps and errors for both; `Surface` used only for `aud` rule (step 9), error hints (portal: "Sign portal links with createPortalLink / portalLink") and metric tags; no other behavior difference. Portal callers (14) pass no app id.

## Claims schema

| Claim | Type | Required | Maps to | Rule |
|---|---|---|---|---|
| `sub` | string | yes | `contacts.external_id`, identity `external_id` verified | 1 to 255 chars |
| `exp` | NumericDate | yes | | seconds |
| `iat`, `nbf` | NumericDate | no | | |
| `aud` | string or array | no | | see step 9 |
| `nonce` | string | no | | single use |
| `email` | string | no | `contacts.email` | addr-spec, max 254, IDN domain to punycode, lowercased domain |
| `email_verified` | boolean | no, default false | `contacts.email_verified`, email identity `verified` | only `true` enables auto-merge by email (R3) |
| `name` | string | no | `contacts.name` | 1 to 120, NFC, bidi controls stripped |
| `phone` | string | no | `contacts.phone` | E.164 |
| `phone_verified` | boolean | no, default false | phone identity `verified` | |
| `avatar_url` | string | no | `contacts.avatar_url` | https only, max 2,048; never fetched server side at session start |
| `locale` | string | no | `contacts.locale` | BCP 47 |
| `timezone` | string | no | `contacts.timezone` | IANA |
| `company` | object | no | `companies` upsert by `(workspace_id, external_id)`; `contacts.company_id` = **primary** company (03 doc, extensibility.md section 10; later `companies` array maps to `contact_companies`, `company` stays primary) | `id` required inside (1 to 255), `name` (1 to 120), `domain` (hostname), `custom_attributes` (data-model rules) |
| `custom_attributes` | object | no | `contacts.custom_attributes` merge + `contacts.trusted_attribute_keys` | data-model rules: max 100 keys total, key `[a-z0-9_]{1,64}`, scalar or string up to 1,024. JWT keys overwrite; `null` value deletes key; absent keys untouched. Every key written by claim added to `trusted_attribute_keys`; `null` removes key from both (07 agent actions bind only trusted keys; widget-set keys never trusted) |
| `custom_attributes.signed_up_at` | number or string | no | `contacts.custom_attributes.signed_up_at` | convention: unix seconds or RFC 3339; 15 segments read it as date. Non-date value kept as given, warning `claim_signed_up_at_invalid` (hint "Use epoch seconds or ISO 8601"). Helpers map user `signedUpAt` |

Unknown top-level claims (incl. flat `company_id`, `user_id`) ignored silently.

Payload example:

```json
{
  "sub": "user_42",
  "exp": 1793530800,
  "iat": 1793527200,
  "email": "ada@acme.com",
  "email_verified": true,
  "name": "Ada Lovelace",
  "company": { "id": "org_7", "name": "Acme", "custom_attributes": { "plan": "pro", "seats": 12 } },
  "custom_attributes": { "role": "admin", "signed_up_at": 1767225600 }
}
```

Header: `{"alg":"HS256","typ":"JWT","kid":"isk_01jbd9..."}`.

## Merge semantics (`IdentifyVisitor`)

Input: workspace, widget, verified claims, current session (may be null, anonymous lead `L`, or identified).

1. `pg_advisory_xact_lock(hashtext(workspace_id || ':' || sub))`: serializes concurrent first logins (two tabs) so one contact results. Unique `(workspace_id, external_id)` is second wall (on conflict: re-read).
2. Find `C` by `external_id = sub` (follow `merged_into_id`, skip deleted).
3. Cases:

| C exists | Session | Action |
|---|---|---|
| no | none or identified (other sub) | create `C` kind `user` |
| no | anonymous lead `L` (kind lead, no verified identities) | upgrade `L` in place: kind `user`, `external_id = sub`. History continues. `contact.updated` with `changes.kind` |
| yes | none or identified (other sub) | use `C` |
| yes | anonymous lead `L` | `MergeContacts(from L, into C, reason "widget_identify", actor system)` (03). `L` conversations move to `C`. `L` unverified email identity moves as unverified; conflict dropped |
| yes | identified same sub | reuse session (extend) |

4. Apply claims to `C` (`ApplyIdentityClaims`; skip all writes when claims hash equals cached hash for `C`, 10 minutes): attributes per schema; every claim-written `custom_attributes` key appended to `contacts.trusted_attribute_keys` (deduped; `null` value removes key); company upsert (company external id from `company.id`); identity rows: `external_id` verified; `email` verified only when `email_verified = true`; `phone` verified only when `phone_verified = true`. Lead (`L`) keys set via widget stay untrusted after upgrade until a claim writes them.
5. Verified email collision: other contact `D` holds verified email identity same value. `D` kind lead: auto-merge `D` into `C` (both verified; foundation merge rule). `D` kind user (other `external_id`): no merge, `C.email` set, no identity row, `contact.updated` with `meta.duplicate_suspect = D` (inbox shows "possible duplicate").
6. Test detection (D10): `email_verified = true` and email equals active member's `users.email` in workspace: session `test = true` (subject to monthly cap, 01).
7. Events: `contact.created` or `contact.updated` (changed keys only), `contact.merged` via 03.
8. Session (01): new identified session with `identity_secret_id`, `external_id = sub`, `verified_at = now`, `expires_at = now + identity.session_ttl` (24 h). Prior session revoked `identity_switch`.

### `IdentifyContact` (14 portal SSO, no widget)

`identity.IdentifyContact{WorkspaceID, Claims, Surface}`: steps 1, 2, 4, 5, 6 above (advisory lock, find/create `C` by `sub`, apply claims via `ApplyIdentityClaims`, verified email collision handling, test detection) without lead upgrade or merge (no session, no lead). Returns contact id + `created` flag. Used by 14 after `VerifyIdentityToken{Surface: portal}`; 14 creates own `portal_sessions`. Events same as step 7.

### Leak-proof rules (test suite `tests/feature/identity/leak_rules_test.go`, one test per rule)

- **R1** Widget never looks up contact by email, phone, or `user_id` from client input.
- **R2** Lead email capture (01 `PATCH /contact`) never creates verified identity, never merges, never claims identity row held by another contact.
- **R3** JWT `email` without `email_verified: true` never auto-merges, never creates verified email identity.
- **R4** Teammate merge of lead into user revokes lead's widget sessions (01 `RepointWidgetSessions`).
- **R5** Plain `user.user_id` stored as `custom_attributes.claimed_user_id` on lead; never `external_id`, never identity row. Plain `user.email` = lead unverified email (R2 rules).
- **R6** Identified session resumes only with JWT whose `sub` equals session `external_id` (`PATCH /widget/v1/session`). `GET /widget/v1/session` on identified session: 409 `identity_proof_required`. Page load with stored identified token and no JWT: SDK sends `DELETE /widget/v1/session` (signs out).
- **R7** Merge of user into user never automatic (different `sub` stay separate even with same verified email: step 5).
- **R8** Widget-side writes to `user` contacts rejected (`identity_locked`); only JWT or REST (03) change verified profile.

## `Dimmi.logout()` semantics

Client (01 sdk-contract): revoke, wipe storage keys `dimmi:{app}:*`, close realtime stream, wipe memory, remount anonymous with no server session. Usually unnecessary: identity source answering `{token: null}` triggers same path (sign-out detection).
Server (`DELETE /widget/v1/session`): revoke this session only (reason `logout`), disconnect its realtime streams, revoke 14 portal sessions with surface `widget` for same widget + contact (01 calls `RevokePortalSessions`). Contact, conversations, other devices untouched. Outbox entries of signed-out user discarded client side (never sent as next anonymous visitor). Host forgot `logout()`: identity source answers `{token: null}`, R6 signs out (handshake `DELETE`; server refuses JWT-less resume).

## Token transport

- Identity source (01 sdk-contract "Identity sources", 02 snippets.md "Model"): Next.js server action, same-origin identity URL `GET /api/dimmi/token` (`200 {"token": "<jwt>" | null}`, `Cache-Control: no-store, private`), identity function, or source object (`getToken`, `subscribe`). SDK asks on page load, navigation, tab visible, `identify()`, 401 `session_expired`/`token_expired`. App code never handles JWTs; helpers map user object to claims.
- Recommended token lifetime: `exp = iat + 600` (10 minutes), minted per request (fetched on demand, so short is free). Max accepted `identity.max_token_lifetime` (7 days) stays as hard cap for custom signers; helpers refuse over 1 hour.
- Never inlined in HTML (page caches, bfcache, Turbo snapshots replay previous user's token). Never in URL, logs, cache.
- Handshake (01 README "Boot handshake"): token sent as wire field `user_jwt` in JSON body. No session or other `sub`: `POST /widget/v1/sessions {app_id, user_jwt, previous_token?}`. Stored identified session same `sub`: `PATCH /widget/v1/session {user_jwt}` (only when claims changed or near expiry; else no request).
- Refresh: `PATCH /widget/v1/session {user_jwt}` (01) extends identified session (admits expired, not revoked); `sub` mismatch 409 `identity_mismatch`.
- Mid-session login: SDK re-asks source (navigation or `identify()`); new token + stored anonymous token = `POST /widget/v1/sessions` with `previous_token` (merge path).
- Invalid JWT on either route: 401 with code below, no side effects (previous session untouched).
- Portal (14): helper SSO route mints token with `aud: "dimmi-portal"`, `exp = iat + 300`, random `nonce`, puts it in URL fragment (never query) of portal SSO page; 14 verifies with `Surface: portal`.

## Data model

One table owned by 02: `identity_secrets` (ownership map). Nonce replay cache lives in Valkey (rebuildable, no table).

### identity_secrets

| Column | Type | Notes |
|---|---|---|
| id | uuid pk | public `isk_...` = JWT `kid` |
| workspace_id | uuid not null | |
| name | text not null | 1 to 60, default "Default" |
| algorithm | text not null CHECK in ('HS256','RS256','EdDSA') | |
| secret_encrypted | bytea | HS256 only, `encryption.Sealed` envelope (`encryption.Seal/Open[string]`) |
| public_key_jwk | jsonb | RS256 (`kty RSA`, n at least 2048 bits) or EdDSA (`kty OKP`, `crv Ed25519`) |
| fingerprint | text not null | HS256: last 4 chars; asymmetric: SHA-256 JWK thumbprint (RFC 7638) |
| status | text not null default 'active' CHECK in ('active','retiring','revoked') | |
| retires_at | timestamptz | required when retiring |
| revoked_at | timestamptz | |
| revoked_reason | text CHECK in ('rotated','compromised','manual','retired') | |
| created_by_member_id | uuid null references workspace_members on delete set null | |
| created_by_token_id | uuid null references personal_access_tokens on delete set null | |
| last_used_at | timestamptz | throttled |
| created_at, updated_at | timestamptz | |

CHECK `(algorithm = 'HS256') = (secret_encrypted IS NOT NULL)`, CHECK `(algorithm <> 'HS256') = (public_key_jwk IS NOT NULL)`. Index `(workspace_id, status)`. Max 5 non-revoked per workspace (action).

Secret value: `dmi_idsec_` + 43 base64url chars (32 random bytes). HMAC key = UTF-8 bytes of whole string (no decoding step for developers). Shown once in create/rotate response. Never retrievable again.

### Nonce replay cache (Valkey, no table)

Key `identity:nonce:{workspace_id}:{sha256(nonce)}`, `SET NX EX` TTL = `exp - now + leeway` (max `identity.max_token_lifetime`). Expiry is TTL: no prune job. Valkey restart loses keys: replay possible until token `exp` (accepted: helper tokens 10 min, portal 300 s; PO rule: Valkey holds only rebuildable state).

### Core table changes

None. `contacts.custom_attributes.claimed_user_id` reserved key (documented, validated: widget/API cannot set it directly except R5 path).

| PATCH | `/api/v1/identity-secrets/{secret}` | identity-secrets.update | `identity:manage` (settings:write) | `name`; `{status: "retiring", retires_at}` (retire, max +30 d); `{status: "revoked", reason, revoke_sessions}` (revoke, default `revoke_sessions: true`) |

No DELETE: revoked rows kept for audit and `token_secret_revoked` messages.

### Secret status changes (`PATCH /api/v1/identity-secrets/{secret}`)

Status enum unchanged: `active`, `retiring`, `revoked` (data model). Each changed field fires own event (rest.md rule 3); `name` alone: no event, audit only.

| From | Body | To | Notes |
|---|---|---|---|
| active | `{status: "retiring", retires_at?}` | retiring | `retires_at` default now + `identity.retire_default` (7 d), max + `identity.retire_max` (30 d). Event `identity_secret.retired`. Action `RetireIdentitySecret` |
| retiring | `{status: "retiring", retires_at}` | retiring | moves date (same bounds); no event |
| active, retiring | `{status: "revoked", reason?, revoke_sessions?}` | revoked | `reason` in (`compromised`, `manual`) stored as `revoked_reason` (default `manual`; `rotated`, `retired` set by system only). `revoke_sessions` default true. Event `identity_secret.revoked` with `sessions_revoked`. Action `RevokeIdentitySecret` |
| retiring | `{status: "active"}` | 422 `invalid_transition` | create or rotate instead |
| revoked | any `status` | 422 `invalid_transition` (`from: revoked`) | terminal |

`retires_at` without `status: "retiring"`: 422. Concurrent status change and rotation: row lock; loser 409 `secret_not_active`.

## Performance, observability

- Secrets decrypted once, cached 5 min in otter keyed `(workspace, kid)` (decrypted material never written to Valkey); Valkey PubSub bust on any secret event (revoke effective cluster-wide under 1 s).
- Zero DB writes in identity step when claims hash unchanged and secret `last_used_at` touched within minute.
- Metrics: `dimmi_identity_verifications_total{result,code}`, `dimmi_identity_verify_seconds` histogram, `dimmi_identity_merges_total{kind=upgrade|merge|collision}`, `dimmi_identity_secrets_active`.
- Logs: workspace, kid, result code, `sub` hashed (SHA-256 prefix 12). Never token, never secret, never claims values.

## Security and privacy

- RFC 8725: alg pinned per key, `none` rejected, no key-type confusion (HS256 key never used as RSA), `crit` rejected, no `jku`/`x5u`/`jwk` header honored (no remote key fetch, no SSRF).
- Constant-time comparisons; try-all-secrets path bounded to 5.
- HS256 secret 256-bit random; RS256 at least 2048-bit; EdDSA Ed25519 only.
- Secret material envelope-encrypted (`encryption.Sealed`); idempotency replay body containing secret stored encrypted; redaction pattern `dmi_idsec_` added to log redactor.
- Claims never trusted for workspace selection: workspace comes from widget app id; token signed by other workspace's key fails `token_kid_unknown`/signature.
- `sub` hashed in client storage (01).
- Audit log: secret create/rotate/retire/revoke.

## Contradictions noted with foundation

- `data-model.md` says `email_verified` true "from verified JWT". This spec narrows: JWT email is verified only with claim `email_verified: true` (host apps often do not confirm emails; trusting them enables account takeover of email-channel history).
- Roadmap says "JWT (HS256) identity verification on by default". MVP has no off switch: every token verified; anonymous visitors still allowed (01 `allow_anonymous`), so verification never blocks first message.

## Open questions (recommended default in bold)

1. RS256/EdDSA public keys at MVP vs HS256 only. **Ship at MVP** (verification code small; lets security-minded teams never share a secret). Snippets cover HS256 only.
2. Identified session TTL: 24 h vs 7 days. **24 h**, renewed by every page-load handshake with fresh JWT (`PATCH /widget/v1/session`); long-lived SPA tabs refresh via identity source (navigation, tab visible).
3. JWT email trust: require `email_verified: true` claim vs trust all JWT emails. **Require claim** (prevents takeover via host apps that skip email confirmation).
