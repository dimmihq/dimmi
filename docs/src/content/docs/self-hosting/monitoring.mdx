---
title: "Monitor your server"
description: "Check health endpoints, tail JSON logs, scrape Prometheus metrics, send OpenTelemetry traces or Sentry errors, and record dashboard sessions."
---

dimmi exposes two public health checks out of the box and optionally exports Prometheus metrics, OpenTelemetry (OTLP) traces, Sentry errors, and recordings of your team's dashboard sessions.

## Health checks

| Endpoint | Response |
| --- | --- |
| `https://support.example.com/up` | `200` with `{"status":"up","release":"<revision>"}` whenever the process is running. |
| `https://support.example.com/ready` | `200` when healthy, or `503` if `database`, `valkey`, or `maintenance` fails. Body marks each check `pass`, `warn`, or `fail`. |

Point your uptime monitor at `/ready`. During maintenance mode ([`dimmi down`](/self-hosting/cli/)), `maintenance` reports `warn` while still returning `200`.

Docker runs `/dimmi health` (which checks `/ready`) every 15 seconds on `web` and every 30 seconds on `worker`. Run `dimmictl status` to view `(healthy)` or `(unhealthy)` beside each container.

## View logs

Follow live logs for all services or specific containers:

```bash
dimmictl logs web worker
```

Logs output one JSON object per line by default. Tune them with `dimmictl set`:

| Variable | Default | Options |
| --- | --- | --- |
| `DIMMI_LOG__LEVEL` | `info` | `debug`, `info`, `warn`, `error` |
| `DIMMI_LOG__DRIVER` | `json` | `json`, `text` |

On servers prepared by the installer, Docker rotates logs at 5 files of 20 MB per container.

## Prometheus metrics

Enable metrics scraping:

```bash
dimmictl set DIMMI_TELEMETRY__METRICS=prometheus
```

`web` and `worker` expose `/metrics` on port `9090` inside the private `dimmi_dimmi` Docker network (never exposed publicly). Attach your Prometheus scraper to `dimmi_dimmi` and scrape `web:9090` and `worker:9090`. When disabled, `/metrics` returns `404`.

## Traces and error tracking

Configure these with [`dimmictl set`](/self-hosting/configuration/):

| Variable | Value |
| --- | --- |
| `DIMMI_TELEMETRY__TRACING` | Set `otlp` to export traces over HTTP (default `none`). |
| `DIMMI_TELEMETRY__OTLP_ENDPOINT` | Collector URL, such as `http://collector:4318/v1/traces`. |
| `DIMMI_TELEMETRY__OTLP_HEADERS__<NAME>` | Extra header on trace exports, such as `DIMMI_TELEMETRY__OTLP_HEADERS__AUTHORIZATION`. |
| `DIMMI_TELEMETRY__SENTRY_DSN` | Sentry DSN for server errors. Reports carry the trace ID and the release. |
| `DIMMI_FRONTEND__ERRORS_DSN` | Sentry DSN for dashboard errors. Must be reachable from your team's browsers. |

Any Sentry-compatible tracker works, such as Sentry, GlitchTip or Rustrak. The server reports failed requests, panics, and background jobs that fail on their last attempt. The dashboard reports its own crashes; failed API calls are left to the server's report. Neither sends email addresses, cookies or request bodies.

With a DSN set, the tracker also gets:

- **Cron monitors.** Every scheduled job checks in when it starts and ends, so a missed, failed or stuck run is flagged.
- **AI runs.** Each agent turn and Operator run is an agent run named after the agent, with its model and tool calls beneath it. A transfer to another agent shows as a handoff in the same trace, and a conversation's runs group together. Model calls made outside any agent, such as ticket summaries, show as runs named `background: <task>`.
- **Web vitals.** The dashboard times page loads and route changes: all of them outside production, a fifth in production.

## Session recordings

Point the dashboard at a [kimmi](https://github.com/dimmihq/kimmi) server and you can replay what a teammate saw when a page broke. Your server records nothing until you set both of these with [`dimmictl set`](/self-hosting/configuration/):

| Variable | Value |
| --- | --- |
| `DIMMI_FRONTEND__SESSIONS_HOST` | Origin of your kimmi server, such as `https://sessions.example.com`. Must be reachable from your team's browsers. |
| `DIMMI_FRONTEND__SESSIONS_KEY` | Public key of the kimmi project to record into, such as `km_pub_0123abcd`. |

dimmi refuses to start with only one of them set, or with a host that carries a path.

Once a teammate signs in, the dashboard loads `kimmi.js` from that host and names the teammate by their dimmi user ID alone, with no name or email. Signing out stops the recording. Help centers, the messenger and your customers' sites never load the recorder, and only the dashboard's Content-Security-Policy allows its host.

On the kimmi side:

- **Allowed origins.** Add your dimmi address, such as `https://support.example.com`, to the project's origins.
- **Masking.** The project's privacy settings decide what leaves the browser. Turn on text and input masking unless your team agrees to record what it reads and types.
