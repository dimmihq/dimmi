---
title: "API versioning and deprecation"
description: "How dimmi versions /api/v1, which additive changes can ship anytime, and how breaking changes and deprecations are handled."
---

dimmi versions its REST API by date. The current version is `2026-11-01` under `/api/v1`, and changes inside a version are strictly additive.

You can check the active version in `info.version` at `/api/v1/openapi.json`, and in the `api_version` field of every [webhook event](/developers/webhooks/receive/).

## Non-breaking changes inside a version

dimmi may ship these at any time, so build clients that safely ignore unknown fields and event types:

- New endpoints, optional query parameters, and optional request fields.
- New fields in JSON responses.
- New webhook event types and envelope fields.
- Additional accepted values on request fields.

Inside a version, dimmi never removes or renames endpoints, parameters, fields, or webhook events, never changes a field's type, never makes an optional field required, and never adds new values to response enums.

## Breaking changes

Any breaking change ships in a new dated API version. The previous version stays live and unchanged for at least 12 months after the new version launches.

## Deprecated endpoints and fields

Deprecated endpoints stay live until their sunset date (at least 12 months after deprecation) and include three HTTP headers on every response:

| Header | Value |
| --- | --- |
| `Deprecation` | `@` followed by the deprecation Unix timestamp (such as `@1793491200`). |
| `Sunset` | HTTP date when the endpoint will be removed. |
| `Link` | URL to migration docs with `rel="deprecation"`. |

The OpenAPI spec marks deprecated routes with `deprecated: true` and `x-sunset`. For deprecated fields, dimmi adds the replacement field beside the old one and keeps sending both.
